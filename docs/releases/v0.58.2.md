# v0.58.2 — 없다고만 확인하던 시험에 있는 쪽을 붙였습니다

v0.58.1에서 이렇게 썼습니다.

> 시험은 전부 통과했습니다 — 그 조합을 보는 시험이 없었으니까요.

같은 릴리즈에 그 문장이 하나 더 해당됐는데 그때는 못 봤습니다.

v0.58.1은 **의미 비교를 못 하는 백엔드에서 묶음 숫자를 내보내지 않는 것**을 시험으로 박았습니다.
그런데 **숫자가 없다는 시험은, 숫자가 아예 나올 수 없어도 똑같이 통과합니다.** 계산을 통째로
지워도 초록이었을 겁니다.

## 나오는 쪽을 붙였습니다

의미 비교가 되는 백엔드에서 미리보기가 실제로 무엇을 내놓는지 확인합니다.

```
semantic: true
지금 (1.1)   묶음 6개 · 37개 묶임 · 가장 큰 묶음 10 · 3개 혼자
바꾸면 (3.5)  묶음 1개 ·  2개 묶임 · 가장 큰 묶음  2 · 38개 혼자
```

변형 둘 다 잡혔습니다: 묶음 계산을 아예 끄면 **묶음 0개**를 잡고, 제안 대신 현재 밴드를 쓰면
**두 칸이 똑같은 것**을 잡습니다.

## 그 시험을 쓰다가 알게 된 것

처음에는 품질 하한 두 개(`semantic_accuracy_bar`, `semantic_purity_bar`)를 낮춰서 내장
임베딩을 의미 백엔드로 만들려고 했습니다. **안 됩니다.**

의미 판정에는 세 번째 조건이 있습니다 — **판별력이 양수일 것.** 그건 설정이 아닙니다.
내장 char-gram 임베딩은 **-0.25** 입니다.

```
판별력 = -0.24989…   쌍별 정확도 = 0.042   최근접 동일 주제 = 0.188
하한을 0.01 / 0.01 로 낮춰도 → semantic: false
```

화면의 안내문은 이미 정확히 이 말을 하고 있었습니다 — "어휘가 뜻을 앞서는 백엔드는 어떤
값으로도 통과하지 못합니다. 그건 설정이 아니라 바닥입니다." 그런데 **코드 주석은 반대로**
"이 값을 낮추면 그런 백엔드에서도 실행된다"고 적혀 있었습니다. 화면이 맞고 주석이 틀렸습니다.
주석을 고치고, 관리자 가이드에도 적었습니다.

두 칸의 설명이 "내장 임베딩은 0.042", "내장 임베딩은 0.188" 이라고 알려 주기 때문에 **그 바로
아래로 낮추면 될 것처럼 보입니다.** 그래서 한 번 더 적을 값어치가 있습니다.

그래서 이 시험은 하한을 낮추는 대신 **품질 측정에 실제로 의미 있는 벡터로 답하는 게이트웨이**를
세웁니다. 패키지에 이미 있던 방식입니다.

## 확인한 것

```
✓ 의미 백엔드에서 묶음 숫자가 나옴 (6묶음 · 37개 · 최대 10 · 3개 혼자)
✓ 묶인 생각 + 혼자 남는 생각 = 임베딩된 생각
✓ 제안한 밴드가 메아리가 아니라 실측 (3.5 → 묶임 급감)
✓ 의미 비교가 안 되는 백엔드에서는 여전히 숫자 없음
```
