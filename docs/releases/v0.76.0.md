# v0.76.0 — 키 없이 MCP 에, 막다른 길 없이 umm 에

Keycloak 이 이미 아는 사람을 두 곳에서 더 알아봅니다. MCP 클라이언트는 키를 복사해 붙이지 않고 Keycloak 에
로그인해 연결하고, 브라우저는 SSO 가 어떤 이유로 실패해도 원문 오류 화면이 아니라 로그인 화면으로 돌아옵니다.
새 스위치는 기본 **꺼짐**이고, 켜기 전까지 `/mcp` 는 v0.75.0 과 같습니다.

## MCP 클라이언트가 Keycloak 로그인으로 연결합니다

지금까지 MCP 에 들어오는 방법은 개인 키 하나였습니다. 설정 화면에서 키를 만들고, 한 번만 보이는 secret 을
복사해 클라이언트 설정에 붙이는 방식입니다. 관리자가 **Keycloak SSO → MCP 클라이언트가 Keycloak 로그인으로
연결하기**(`oidc.mcp_oauth`)를 켜면 클라이언트에는 주소 하나만 등록하면 됩니다.

```
    클라이언트                     umm                                  Keycloak
       │  POST /mcp (자격 없음)       │                                      │
       │ ───────────────────────────▶│                                      │
       │  401  resource_metadata="…/.well-known/oauth-protected-resource/mcp"
       │  GET 그 문서 → issuer · scopes_supported                          │
       │  브라우저에서 로그인 · PKCE 코드 교환 ──────────────────────────────▶│
       │ ◀────────────────────────────────────────────── access token ─────│
       │  POST /mcp  Bearer <token> ─▶│  서명 · iss · aud · exp → sub → 사용자, scope → 권한
```

umm 은 MCP 인가 흐름(RFC 9728 + OAuth 2.1)의 **리소스 서버**만 맡습니다. 등록 · 로그인 화면 · 토큰 갱신은
Keycloak 과 클라이언트 사이의 일입니다.

- **권한은 토큰의 `scope`** 입니다. 이름이 키 scope 와 같은 Keycloak Client Scope(`notes:read` 등)를 만들어 두면
  각 도구는 키에 묻던 질문을 토큰에도 똑같이 묻습니다
- **키 정책을 넘지 못합니다.** **키 · 권한** 에서 허용하지 않은 scope 는 토큰에 있어도 무시되고, 메타데이터의
  `scopes_supported` 에도 실리지 않습니다
- **사람은 그대로입니다.** `sub` 는 SSO 로그인과 같은 `oidc_subject` 입니다. 처음 보는 사람은 로그인 화면과 같은
  그룹 매핑으로 만들어지고, 이미 있는 사람의 역할과 비활성 상태는 토큰이 바꾸지 않습니다
- **`aud` 가 umm 이어야 합니다.** 기본값은 `<공개 URL>/mcp` 입니다. 같은 Realm 의 다른 서비스용 토큰은 서명이
  맞아도 거절됩니다
- 거절되면 `error="invalid_token"` 만 답하고 이유는 서버 로그에 남깁니다

Keycloak 쪽에는 PKCE Public Client, Audience 매퍼, Client Scope 셋이 필요합니다. 절차는 관리자 가이드
**부록 2-2** 에 있습니다.

## SSO 가 실패해도 로그인 화면으로 돌아옵니다

v0.75.0 의 자동 로그인에는 사람을 가두는 길이 넷 있었습니다.

| 상황 | 전 | 후 |
| :--- | :--- | :--- |
| 자동 로그인 중 Keycloak 무응답 | API 주소에 `503 dial tcp …`, 새로고침해도 같은 화면 | `/login?sso=error` |
| state 만료 · 코드 교환 실패 · 토큰 검증 실패 | 원문 텍스트 | `/login?sso=error` |
| 자동 로그인 거절 | `/login?sso=none`, 열던 주소는 잃음 | `return_to` 를 가져감 |
| 로그인 화면의 SSO 버튼 | 항상 `/` 로 돌아옴 | 열던 주소로 돌아옴 |

v0.75.0 노트의 "하지 않은 것" 에 적었던 마지막 줄이 이번에 해결됐습니다. 이유는 화면이 아니라 서버 로그에
`OIDC login could not start` 또는 `OIDC callback failed reason=<단계>` 로 남습니다. `return_to` 는 이제 `\`
가 든 경로도 거부합니다. 브라우저가 `/\evil.example` 을 `//evil.example` 로 읽기 때문입니다.

## 로그인 화면은 조직 계정이 먼저입니다

사내 앱 스토어의 로그인 화면과 같은 구성입니다. SSO 가 켜진 설치에서는 **조직 계정으로 로그인** 이 첫
단추입니다. 아이디 · 비밀번호 칸은 **아이디와 비밀번호로 로그인** 아래에 접힙니다. 자동 로그인이 거절되면
오류가 아니라 조직 계정 세션이 없다는 안내가 뜹니다. SSO 가 방금 실패했을 때는 비밀번호 칸이 펼쳐진 채로
열립니다. SSO 가 꺼진 설치의 화면은 그대로입니다.

## 운영자가 알아야 할 것

- 마이그레이션은 없습니다. `oidc` 설정 절에 `mcp_oauth` · `mcp_audience` 두 값이 더해졌고, 없으면 꺼짐입니다
- 새 경로 둘: `GET /.well-known/oauth-protected-resource` 와 `…/mcp`. 스위치가 꺼져 있으면 404 입니다
- `/api/v1/meta` 에 `mcpOAuth` 가 더해졌습니다
- Keycloak Discovery 결과를 10분 캐시합니다. 연결 시험 버튼은 캐시를 거치지 않습니다
- 공개 URL(일반 설정)이 MCP 토큰의 리소스 식별자입니다. 정확해야 합니다
- grpc 를 1.83.1 로 올렸습니다. 1.83.0 에서 HTTP/2 DATA 프레임을 잘게 나눠 보내면 메모리가 끝없이 늘어나는
  GO-2026-6348 이 공개되었고, umm 은 Dream 스케줄러의 OpenTelemetry 내보내기로 그 코드에 닿습니다

## 확인한 것

```
✓ mcp_oauth 꺼짐: 토큰은 낯선 값, 예전 문구 그대로, challenge 없음, 메타데이터 404, 사용자 생성 없음
✓ 켜짐: 자격 없으면 메타데이터 주소를 가리키는 challenge, 잘못된 토큰은 invalid_token 만
✓ 메타데이터: resource · issuer · 허용된 도구 scope 만
✓ 토큰 scope 중 정책이 허용한 것만 권한, 요청하지 않은 scope 는 없음
✓ 처음 보는 사람은 그룹 매핑으로 생성·감사 기록, 바뀐 역할과 비활성은 토큰이 되돌리지 않음
✓ 다른 aud · 다른 issuer · 만료 · 모르는 키 → 거절, 사용자 생성 없음
✓ 키는 그대로 통과, 브라우저 세션은 그대로 거절
✓ 거절 시 return_to 유지 · 모르는 state · 교환 실패 · Keycloak 무응답 → /login?sso=error
✓ /\evil.example 은 / 로
✓ 브라우저: Keycloak 을 끈 채 /space/abc 를 열면 /login?sso=error&return_to=%2Fspace%2Fabc
✓ 브라우저: 거절 화면에서 비밀번호로 로그인하면 가져간 주소(/dreams)로
```

## 하지 않은 것

- **로그아웃해도 Keycloak 세션은 남습니다.** 새 탭을 열면 자동 로그인이 다시 됩니다. 막으려면 Keycloak 의
  end-session 까지 이어야 합니다
- **웹 로그인의 nonce · PKCE.** 사내 앱 스토어는 쓰지만 umm 은 아직 쓰지 않습니다. verifier 를 저장할
  마이그레이션이 필요합니다
- **실제 Keycloak 과 실제 MCP 클라이언트로 한 확인.** 이 환경에는 둘이 없어서, 서명한 토큰을 내주는 대역
  Keycloak 으로 통합 시험을 했습니다. redirect URI 와 동적 등록 필요 여부는 클라이언트마다 다르니 첫 연결 때
  부록 2-2 대로 확인하세요
