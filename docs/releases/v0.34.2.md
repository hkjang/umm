# v0.34.2 — 연결 테스트가 엉뚱한 서버를 보고 있었습니다

v0.34.1에서 자동 찾기를 고쳤습니다. 같은 자리에 **연결 테스트** 버튼이 있어서 그것도 확인했더니,
서버 쪽이 새 칸을 **아예 읽지 않고** 있었습니다.

```go
var body struct {
    BaseURL string `json:"base_url"`      // 채팅 주소
    APIKey  string `json:"api_key"`       // 채팅 키
    Model   string `json:"embedding_model"`
}
```

화면은 `embedding_base_url`·`embedding_api_key`를 보내고 있었고, 서버가 버리고 있었습니다.

## 왜 나쁜가

임베딩 서버를 따로 둔 사람이 **연결 테스트를 누르면 채팅 서버를 임베딩 모델 이름으로 찔러 봅니다.**

- 실패하면 → 멀쩡한 임베딩 설정을 잘못된 것으로 오해합니다
- 성공하면 → **더 나쁩니다.** 실제로 임베딩이 가는 곳과 다른 서버가 초록불을 켜 줍니다

**아무 의미 없는 초록불은 빨간불보다 나쁩니다.**

## 고친 방법

주소를 정하는 규칙을 **한 곳에** 두고 런타임과 테스트가 같이 씁니다.

```go
store.ResolveEmbeddingEndpoint(baseURL, apiKey, embeddingBaseURL, embeddingAPIKey)
```

규칙을 두 벌 적어 두는 것이 바로 이 둘이 어긋난 이유였습니다. 이제 **테스트가 초록이면 실제로
임베딩하는 그 서버가 초록**입니다.

키 규칙도 그대로 따릅니다. 임베딩 주소를 지정하면 채팅 키는 그쪽으로 가지 않고, 임베딩 키가
**비어 있으면 인증 없음**입니다. 마스킹된 값(`••••••••`)만 "저장된 것 그대로"를 뜻합니다 — 빈 값을
저장된 키로 채우면 인증이 필요 없는 서버에 굳이 키를 보내게 됩니다.

## 테스트

서버 두 개를 띄워 놓고 확인합니다. 채팅 쪽은 요청이 오면 **418로 거절**하고, 임베딩 쪽만 정상
응답합니다.

- 임베딩 서버가 호출됐는가
- 채팅 서버는 **한 번도** 호출되지 않았는가
- 채팅 키가 임베딩 서버로 새지 않았는가

고치기 전 코드로 돌려 실패를 확인했습니다.

```
the embedding server answered but the test failed:
  embedding gateway status 418: the chat gateway should not be asked to embed
```

임베딩 주소를 비워 두면 예전처럼 채팅 주소를 테스트한다는 것도 함께 고정했습니다.

## 확인한 것

- 전체 Go 테스트 통과, 웹 53개 통과, 타입·린트 통과
- 새 테스트를 고치기 전 코드로 돌려 실패 확인
