# v0.49.2 — 읽기 전용 멤버가 남의 공간에 연결을 쓰고 있었습니다

읽기 전용 작업을 마무리하려고 **툴바에 남은 것들**을 확인하다가, UI 문제가 아니라 **권한
구멍**을 찾았습니다.

## 읽기 전용 멤버가 연결 4개를 썼습니다

`연결 추천 받기` 는 추천을 **저장합니다.** 즉 읽기가 아니라 남의 작업 공간을 바꾸는
일입니다.

메모 수정은 쓰기 권한을 확인합니다. 이 경로는 하지 않았습니다 — **메모를 읽고**(읽기 전용
멤버도 됩니다) 곧바로 **엣지를 넣었습니다.**

```
읽기 전용 멤버가 SuggestLinks 호출
  → "a read-only member was handed 4 new edges"
  → "a read-only member added 4 edges to a space they may only read"
```

일반 엣지 생성 경로에는 **이미 올바른 조건이 있었습니다.**

```sql
WHERE EXISTS(... s.owner_id=$5 OR m.permission IN ('edit','manage'))
```

추론 엣지 경로만 그걸 쓰지 않고 있었습니다. **새 규칙을 만든 게 아니라 빠진 자리에
적용했습니다.**

## 두 곳에서 막습니다 — 다만 역할이 다릅니다

정직하게 적어 둡니다. **둘의 무게가 같지 않습니다.**

```
앞단 거절만 남기고 INSERT 가드 제거   → 테스트 통과   (앞단이 실제로 막고 있음)
INSERT 가드만 남기고 앞단 제거        → 엣지는 안 써지지만 no rows 로 500
```

즉 **지금 동작을 지키는 건 앞단 거절**이고, INSERT 가드는 *미래의 다른 호출자* 를 위한
것입니다. 그 경우에도 데이터는 지키지만 응답이 나빠집니다. 방어를 두 겹으로 둔 이유는
이것이고, 둘이 똑같이 필요한 것처럼 적지 않겠습니다.

권한은 **임베딩을 재기 전에** 묻습니다. 더 근본적인 거절이고, 쓸 수 없는 사람을 위해 임베딩
품질을 측정할 이유가 없습니다.

## 화면에서도 내놓지 않습니다

읽기 전용 공간에서는 `연결 추천 받기` 를 아예 보여 주지 않습니다. 혹시 도달하더라도
`read-only` 결과를 **"가까운 것이 없었습니다"가 아니라** 그대로 설명합니다 — 그건 사실이
아니니까요.

## 검증

```
✘ 앞단 거절 제거          → 500 (no rows)
✘ INSERT 가드 제거        → 통과 (앞단이 막음) ← 그래서 위처럼 적었습니다
✘ 화면에서 권한 무시      → 버튼이 남아 실패
✓ 소유자·편집 멤버        → 그대로 동작함을 함께 검사
```

## 제 테스트가 전체 실행에서만 실패했습니다

새로 쓴 메뉴 테스트가 **단독으로는 통과하고 전체 스위트에서는 실패**했습니다. 원인은 제
쪽이었습니다 — `menuitem` 을 페이지 전체에서 찾고 있어서 **앞 테스트가 남긴 메뉴**를 같이
잡았습니다. 열린 드롭다운으로 범위를 좁히고, 호버로만 나타나는 버튼을 기다리도록 고쳤습니다.
