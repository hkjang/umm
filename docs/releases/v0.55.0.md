# v0.55.0 — 감사 로그에 질문을 할 수 있습니다

관리 기능 고도화, 첫 번째입니다.

감사 로그는 남길 만한 것을 **다 남기고 있었습니다** — 공간 공유 회수, 키 회전, 메모 복원,
다른 기기 로그아웃까지. 그런데 읽는 방법은 **최신순 전부**, 그것 하나뿐이었습니다.

> "누가 이 사람을 저 공간에서 뺐지?"

이 질문에 답하려면 **계속 늘어나기만 하는 로그를 끝까지 스크롤**해야 했습니다. 그건 답을
얻는 방법이 아닙니다.

## 이제 좁혀서 볼 수 있습니다

```
행위자      아이디, 또는 system
작업        로그에 실제로 있는 작업 목록에서 고릅니다
대상 ID     공간·메모·키의 ID
기간        from / to (API)
```

조건은 **서로 합쳐집니다.** `행위자=alice` + `작업=space.unshare` 는 둘 다 만족하는 것만
보여 줍니다.

**작업 목록은 하드코딩이 아닙니다.** 최근 기록에 실제로 있는 작업 이름을 서버가 돌려주므로,
`space.unshare` 를 한 글자도 틀리지 않게 타이핑할 필요가 없고, 새 작업이 생기면 목록에 저절로
나타납니다.

## 없는 것과 못 찾은 것

조건에 맞는 기록이 없으면 이렇게 말합니다.

> 이 조건에 맞는 기록이 없습니다. 기록이 없다는 뜻이지, 찾지 못했다는 뜻이 아닙니다.

없는 작업 이름이나 없는 아이디로 물어보면 **조용히 무시하고 전체를 보여 주지 않습니다.**
적용되지 않은 필터는 빈 페이지보다 나쁩니다 — 그 페이지가 답처럼 보이니까요.

## 조건 지우기가 지우지 않던 문제

만들면서 하나 잡았습니다. `조건 지우기` 는 조건을 비우고 **곧바로** 다시 검색하는데, 방금
설정한 상태는 그 자리에서 읽을 수 없습니다. 그래서 **방금 지운 조건 그대로** 다시 검색하고
있었습니다.

이제 지운 조건을 **넘겨 줍니다.** 되돌려서 확인했습니다 — 목록이 돌아오지 않아 시험이
실패합니다.

## 시험을 하나로 묶었다가 낭패

처음엔 세 가지를 한 시험에 넣었더니 **1분을 넘기고 마지막 클릭에서 멈췄습니다.** 버튼이
문제인 줄 알고 가려짐·클릭 가능 여부까지 다 재 봤는데 전부 정상이었고, 같은 동작을 따로 떼서
돌리면 **5초**에 끝났습니다. 셋으로 나누니 12초에 전부 통과합니다.

**서버 바이너리를 다시 빌드하지 않아** 필터가 안 먹는 것처럼 보인 일도 있었습니다. 번들만
다시 만들고 서버는 옛것이었습니다.
