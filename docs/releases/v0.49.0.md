# v0.49.0 — 읽기 전용으로 공유된 공간이 그렇게 보입니다

이 세션 내내 계정 하나로만 써 봤습니다. **두 번째 사람을 만들어 공간을 공유해 봤습니다.**

## 서버는 정확했습니다

읽기 권한만 가진 사람이 API 로 할 수 있는 것을 전부 눌러 봤습니다.

```
메모 수정      403
메모 추가      404
메모 삭제      404
다시 공유      403
댓글           201    ← 의도된 것. 못 고쳐도 이야기는 할 수 있습니다
```

## 화면은 소유자와 똑같았습니다

```
              소유자    읽기 전용 사용자
편집기 잠김     아니오       아니오      ← 타이핑이 됩니다
캡처 바         있음         있음
메모 메뉴       있음         있음
읽기 전용 안내   없음         없음
```

그래서 이렇게 됩니다.

```
읽기 전용 사용자가 메모에 타이핑 → 포커스를 뗌
  → PUT 403
  → 글자가 서버 내용으로 되돌아감
  → "요청 오류 · 이 공간의 편집 권한이 없어 오프라인 변경을 적용할 수 없습니다."
```

**쓴 글이 사라지고 나서야 알게 됩니다.** 게다가 그 문구는 *오프라인* 을 위해 쓰인 것인데
온라인에서 방금 타이핑한 사람에게 나옵니다.

## 화면이 알 방법이 없었습니다

`/spaces` 응답에 권한이 없었습니다. `ownerId` 만으로는 **편집 가능한 멤버와 읽기 전용 멤버가
똑같아 보입니다.** 이제 서버가 각 공간마다 **그 사람이 무엇을 할 수 있는지** 함께 보냅니다.

```
소유자           permission=manage
편집 가능 멤버    permission=edit
읽기 전용 멤버    permission=view
```

권한은 **목록을 만드는 바로 그 행에서** 가져옵니다. 다른 곳에서 따로 계산하면 둘이 서로 다른
말을 하기 시작합니다.

캔버스는 이제 이렇게 합니다.

```
편집기          읽기 전용, placeholder "읽기 전용으로 공유된 생각입니다"
캡처 바 자리     "읽기 전용으로 공유된 공간입니다. 댓글은 남길 수 있습니다."
```

캡처 바를 **그냥 없애지 않고 안내로 바꿉니다.** 없애기만 하면 화면은 평범해 보이고 왜
없는지는 아무도 모릅니다.

## 검증

되돌려서 확인했습니다.

```
✘ 모두에게 manage 를 주도록         → edit·view 가 manage 로 나와 실패
✘ 캔버스가 권한을 무시하도록         → 편집기가 잠기지 않아 실패
✓ 쓸 수 있는 공간은 그대로          → 안내 없음·캡처 바 있음을 함께 확인
```

마지막 줄이 중요합니다. **쓸 수 있는 공간을 잠그는 건 더 나쁜 고장**이라 그쪽도 테스트로
묶어 두었습니다.

## 제 측정이 또 틀렸습니다

처음엔 "아무 안내 없이 조용히 사라진다"고 판단했습니다. 실제로는 **안내가 있었고**, 제
선택자가 `.mantine-Notification-root` 였는데 실제 클래스가 달라서 못 잡은 것이었습니다.

이번 세션에서 **세 번째**입니다 — 캔버스 확대율 두 번, `navigator.onLine` 한 번. 결함이라고
믿기 전에 **내 측정이 올바른 코드에서도 그 값을 낼 수 있는지** 먼저 확인하는 습관만이
매번 이걸 잡아냅니다.
