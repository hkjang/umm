# v0.53.3 — "없습니다" 와 "못 했습니다" 는 다른 말입니다

웹훅 삭제는 **무슨 일이 생기든 404 "웹훅을 찾을 수 없습니다"** 라고 답했습니다.

```go
command, err := s.Store.Pool.Exec(...)
if err != nil || command.RowsAffected() == 0 {
    writeError(w, 404, "웹훅을 찾을 수 없습니다.")
```

데이터베이스가 잠깐 흔들려서 삭제가 실패해도 **"그런 웹훅은 없습니다"** 라고 말합니다.
받는 사람 입장에서는 이미 지워진 것으로 보이니 다시 시도하지 않습니다. 그런데 웹훅은
살아 있고, **메모는 계속 그쪽으로 갑니다.** 여기서 틀리면 가장 나쁜 방향으로 틀립니다.

같은 방식이 여섯 군데 있었습니다.

```
웹훅 수정 · 웹훅 삭제 · 웹훅 비밀키 교체
알림 읽음 표시 · 사용자 수정(관리자) · AI 평가 케이스 삭제
```

관리자가 사용자를 **비활성화**하려다 실패해도 "사용자를 찾을 수 없습니다" 였습니다.

이제 둘을 나눕니다 — 실패는 500 과 무엇을 못 했는지, 없는 것은 404.

## 어떻게 찾았나

웹훅 삭제를 시험으로 고정하다가 나왔습니다. 삭제가 **이미 대기 중인 전송까지 없애는지**
확인하려고 스키마에서 `ON DELETE CASCADE` 를 떼어 봤더니, 삭제가 실패하면서 핸들러가
404 를 돌려줬습니다. 되돌리기가 의도한 것과 다른 것을 알려 준 셈입니다.

## 검증

실패를 **상상하지 않고 실제로 만들었습니다.** 시험 전용 스키마에서 전송 테이블의 외래키
cascade 를 떼어, 핸들러가 실행하는 바로 그 문장이 진짜로 실패하게 했습니다.

```
✘ 예전처럼 err 과 0행을 같이 취급        →  404 를 돌려줌 ("웹훅을 찾을 수 없습니다")
✓ 이제                                  →  500, "웹훅을 삭제하지 못했습니다"
                                           그리고 웹훅은 여전히 목록에 있습니다
```

없는 웹훅을 지우려 하면 **여전히 404** 입니다. 나눈 것이지 뭉갠 것이 아닙니다.

## 함께: 웹훅을 지우면 이미 대기 중인 전송도 사라집니다

이건 원래 그렇게 동작하고 있었지만 아무것도 붙잡고 있지 않았습니다. `ON DELETE CASCADE`
하나에 기대고 있는데, 스키마를 다시 쓰다가 빠지면 **취소가 취소를 뜻하지 않게 됩니다.**

```
✘ cascade 제거  →  삭제 자체가 외래키 위반으로 실패
```

## 제 시험이 이웃을 깨뜨린 일

이 패키지의 시험들은 **하나의 데이터베이스를 함께 씁니다.** 처음 쓴 시험은 구독을 남겨
두었고, 다음 시험의 `Enqueue` 가 구독 하나당 한 건씩 넣기 때문에 1건이 아니라 2건이
됐습니다. 옆 시험 두 개가 제 탓에 실패했습니다.

사용자만 지우고 cascade 를 기대한 것이 잘못이었습니다. 이제 구독·공간·사용자를 손으로
지웁니다. 그리고 "보내질 차례였다" 는 확인도 데이터베이스 전체에서 다음 전송을 집어 오는
대신 **이 구독의 것만** 셉니다 — 함께 쓰는 데이터베이스에서 먼저 온 남의 전송을 집어 오던
문제였습니다.
