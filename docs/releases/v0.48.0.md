# v0.48.0 — 마우스 없이도 본문에 닿습니다

화면은 데스크톱과 휴대폰으로 다 봤지만, **키보드만으로 써 본 적은 없었습니다.**

## 본문에 닿기까지 12번을 눌러야 했습니다

새로 연 페이지에서 Tab 을 세어 봤습니다.

```
 1. 로고        2. 무슨 생각을...   3. 빠른 이동    4. 알림    5. 프로필
 6. 오늘의 리뷰   7. My Space      8. Dreams     9. 결정 기록
10. 검토·승인   11. 개인 설정      12. 서비스 관리자
─────────────────────────────────────────────────
13. 드디어 본문
```

헤더 5개와 사이드바 7개. **페이지를 열 때마다 매번 열두 번**입니다. 건너뛰기 링크는
없었습니다.

이제 **한 번**입니다. 첫 Tab 에 나타나고, Enter 로 본문에 초점을 옮깁니다.

```
첫 Tab   → "본문으로 건너뛰기"  (초점이 오면 화면에 나타남)
Enter    → <main> 으로 초점 이동
다음 Tab → 본문의 첫 컨트롤     ← 헤더로 되돌아가지 않습니다
```

`display: none` 이나 `visibility: hidden` 이 아니라 **화면 밖으로 밀어 두었습니다.** 그 둘은
요소를 탭 순서에서 빼 버리는데, 그러면 이 링크가 존재할 이유가 없어집니다.

## 그러다 더 큰 걸 찾았습니다: main 이 두 개였습니다

초점을 어디로 보낼지 정하려다 알았습니다.

```
/today      <main> ×2  (중첩 1)   ["m_8983817", "today-page"]
/dreams     <main> ×2  (중첩 1)
/settings   <main> ×2  (중첩 1)
/admin      <main> ×2  (중첩 1)
```

Mantine 의 `AppShell` 이 이미 본문 영역을 `<main>` 으로 그리는데, **각 페이지가 그 안에 또
하나를 그리고 있었습니다.** 중첩된 `main` 은 유효하지 않은 HTML 이고, 랜드마크로 이동하는
사람에게는 **같은 이름의 목적지가 두 개** 나타납니다 — 어느 쪽이 본문인지 알 방법 없이요.

건너뛰기 링크가 이걸 구체적으로 만들었습니다. **초점을 보낼 후보가 둘이었습니다.**

이제 페이지마다 하나입니다. 캔버스의 선형 목록은 이름표가 있으니 `<section aria-label>`
으로 바꿨습니다.

```
후:  /today /canvas /dreams /decisions /approvals /settings /admin  →  전부 <main> ×1
```

CSS 는 전부 클래스로 선택하고 있어서 태그를 바꿔도 스타일은 그대로입니다. 스크롤도
그대로입니다 — 스크롤 검사는 원래 **바깥쪽(셸) main** 을 재고 있었고, 그건 바뀌지
않았습니다.

## 검증

되돌려서 확인했습니다.

```
✘ 건너뛰기 링크 제거          → 3개 실패
✘ display:none 으로 숨김      → 3개 실패 (탭 순서에서 빠짐)
✘ 중첩 main 을 한 페이지에 복원 → "/today has 2 main landmarks" 로 실패
```

세 번째는 **처음에 잘못 쟀습니다.** 태그만 바꾸고 닫는 태그를 안 맞춰서 빌드가 깨졌고,
브라우저는 **이전 번들을 그대로 받고 있었습니다.** 그래서 테스트가 통과했고, 저는 하마터면
"이 테스트는 못 잡는다"고 결론 내릴 뻔했습니다. 빌드 오류를 확인하고 `git show HEAD:` 로
**실제 변경 전 파일**을 되돌려 다시 재니 제대로 실패했습니다.

**되돌리기가 진짜로 적용됐는지부터 확인해야 합니다.** 조용히 실패한 빌드는 통과하는
테스트처럼 보입니다.

## 제 변경이 제 테스트를 깨뜨렸습니다

`main.settings-page` 로 요소를 찾던 이전 스펙 두 개가 실패했습니다. 태그를 바꿨으니
당연합니다. **테스트가 제대로 잡아 준 것**이고, 선택자를 태그와 무관한 `.settings-page` 로
고쳤습니다.
