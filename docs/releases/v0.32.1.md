# v0.32.1 — 캔버스를 열 때마다 같은 계산을 두 번 했습니다

압축을 재다 보니 이상한 게 있었습니다. 캔버스 응답이 회선에서는 65KB인데 **서버가 3초**를 씁니다.

SQL을 직접 재 봤습니다.

```
생각 2,010개 조회   6.2ms
연결 조회           3.7ms
```

**데이터베이스가 아니었습니다.** 전부 Go 쪽이었습니다.

## 무엇을 하고 있었나

`ListNotes` — **캔버스를 열 때마다 도는 경로** — 는 각 생각에 붙는 `관련 N` 칩을 위해 두 번 훑고
있었습니다.

1. 모든 쌍의 유사도를 구해 **기준선**을 계산 (n(n-1)/2 회)
2. 그 기준을 넘는 개수를 세려고 **정사각형 전체를 다시** 돌며 코사인을 **처음부터 다시 계산** (n² 회)

2,010개면 약 **200만 + 400만 = 600만 번**의 벡터 연산입니다. 작은 칩 하나를 위해서요.

2번은 1번이 이미 구한 값을 **버리고 다시 구하고 있었습니다.**

## 지금은

이미 구한 점수를 그대로 읽습니다. 유사도는 대칭이므로 쌍마다 한 번 보고 **양쪽에 각각 세면** 정사각형이
주던 답과 같습니다.

```
캔버스 응답  3.05s → 1.10s   (2.8배)
벡터 연산    600만 → 200만
```

**결과는 한 글자도 다르지 않습니다.** 테스트가 예전 방식(정사각형 전체)으로 센 값과 새 방식의 값을
직접 비교합니다.

## 남아 있는 것

이 경로는 여전히 O(n²)입니다. 5,000개짜리 공간이면 다시 느려집니다. 다만 지금 고칠 수 있는 건
**같은 일을 두 번 하던 것**이었고, 경계를 두는 것은 `관련 N`이 "계산하지 않음"과 "관련 없음"을
구분해 말할 수 있어야 하는 별개의 설계입니다. 지금은 둘 다 칩이 사라져서 구분되지 않습니다.

## 확인한 것

- 새 계산이 예전 정사각형 계산과 **같은 값**을 내는지 통합 테스트로 고정
- 전체 Go 테스트 통과
- 실행 중인 인스턴스에서 3회 측정
