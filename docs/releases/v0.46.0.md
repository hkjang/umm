# v0.46.0 — Dreams가 몇 개인지 정확히 말합니다

남은 화면을 하나씩 열어 봤습니다. `검토·승인`은 비어 있는 이유를 정확히 설명하고 있었고,
`개인 설정`은 Dream이 꺼져 있다는 걸 말하며 관련 항목을 비활성화해 두고 있었습니다.
문제는 **Dreams**에 있었습니다.

## 탭의 숫자가 페이지를 세고 있었습니다

37개가 기다리는 계정에서 잰 값입니다.

```
도착했을 때        검토함 30   (카드 30장)
'이전 Dream 더 불러오기' 누름
그 다음             검토함 37   (카드 37장)
```

목록은 30개씩 옵니다. 탭은 **도착한 것**을 세고 있었으니, 센 것은 대기열이 아니라
**페이지**였습니다. 게다가 숫자가 바뀌는 계기가 *"이전 Dream 더 불러오기"* — 대기열이
아니라 **지난 기록**에 대한 버튼입니다.

같은 순간, 홈 화면은 이렇게 말하고 있었습니다.

| 화면 | 표시 | 실제 |
| --- | --- | --- |
| 홈 타일 `새 Dream` | **37** | 37 ✓ |
| Dreams 탭 `검토함` | **30** → 누르면 37 | 37 ✗ |

**한 제품의 두 화면이 같은 것을 두고 다른 숫자를 말하고 있었고, 틀린 쪽은 상관없는 것을
누르면 움직였습니다.**

이제 서버가 상태별로 세어 보냅니다. 네 탭 모두 숫자를 답니다.

```
검토함 37   채택됨 0   숨김 0   전체 37
```

세는 범위는 목록의 조건을 그대로 옮겨 적었습니다 — 같은 사용자, 같은 접근 가능한 공간.
**자기가 붙은 목록과 다른 규칙으로 센 숫자**가 애초에 이 문제의 출발점이었습니다.

### 숨기면 숫자도 따라 움직입니다

고치면서 같은 함정을 새로 팔 뻔했습니다. `숨기기`는 목록만 손대고 있어서, 그대로 두면
탭은 37에 멈춘 채 카드만 36장이 될 참이었습니다. 서버에 다시 물어봅니다 — 이 페이지가
어느 쪽으로 옮겨졌는지 알고 있는데도요. **상태와 탭의 대응 규칙을 두 군데 두는 순간**
다시 어긋나기 시작하기 때문입니다.

```
숨기기 전   검토함 37 · 숨김 0 · 전체 37
숨긴 뒤     검토함 36 · 숨김 1 · 전체 37
```

## 타임라인이 날짜를 29번 말했습니다

한 페이지를 다 불러온 상태에서 셌습니다.

```
날짜 머리글 29개  ·  실제 날짜 2개
```

카드마다 자기 날짜를 달고 있었습니다. **하루가 어디서 끝나고 다음 날이 어디서 시작하는지**
— 타임라인이 있는 이유가 바로 그건데, 그것만 볼 수 없었습니다. 이제 그날의 첫 Dream에만
날짜가 붙습니다.

```
날짜 머리글 2개  ·  실제 날짜 2개
```

날짜는 **읽는 사람의 형식으로 비교**합니다. 타임스탬프가 아니라요 — 자정을 사이에 둔 한
시간 차이는 그 사람에게 다른 날이고, 그걸 정하는 건 UTC가 아니라 그 사람의 지역과 달력을
쓰는 형식기입니다.

## 검증

전부 되돌려서 확인했습니다.

```
✘ 세는 범위를 한 줄로 자름         → inbox 35(want 37) 로 실패
✘ 공간 범위 조건 제거              → 남의 Dream 43개까지 셈, 실패
✘ exposed 를 대기열에서 제외       → inbox 35(want 37) 로 실패
✘ 탭 라벨을 다시 목록에서 계산     → E2E 둘 다 실패
✘ 모든 항목에 날짜를 다시 달기     → 머리글 9개(want 2) 로 실패
✘ 첫 항목에만 날짜를 달기          → 머리글 1개(want 2) 로 실패
```

마지막 두 개는 방향이 반대입니다. **너무 많이 붙이는 것과 너무 적게 붙이는 것을 각각**
잡지 못하면, 통과하는 테스트가 무엇을 지키는지 알 수 없습니다.
