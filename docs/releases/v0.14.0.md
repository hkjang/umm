# umm v0.14.0 — 판정 기준을 관리자에게

지금까지 umm이 "가깝다"고 판단하는 기준은 전부 바이너리 안의 상수였습니다. 연관 생각의 문턱, 군집으로 묶는 지점, 검색 라벨, 자동 연결이 실행될 자격, 한 번에 제안할 개수 — 전부입니다.

측정해서 정한 값들이고 좋은 기본값입니다. 하지만 **한 데이터셋, 두 언어로 측정한 값**입니다. 좁은 도메인 하나만 다루는 배포, 한 언어만 쓰는 배포, 짧은 메모 위주인 배포는 다른 선이 필요할 수 있고, 지금까지 그걸 알아낼 방법은 umm을 다시 빌드하는 것뿐이었습니다.

이제 설정입니다. **기본값은 측정한 그 값 그대로이므로, 아무것도 바꾸지 않으면 동작이 완전히 같습니다.**

---

## 1. 관리자 → 유사도 기준

| 항목 | 기본 | 뜻 |
| :--- | ---: | :--- |
| 연관 생각 기준 | 0.6 | 낮을수록 더 많이 연관으로 봅니다 |
| 군집 기준 | 1.1 | 한 주제로 묶는 문턱 |
| 강한 일치 기준 | 0.9 | 검색에 "의미상 유사" 라벨을 붙이는 문턱 |
| 자동 연결 사용 | 켬 | 끄면 그래프에 사람·에이전트가 넣은 연결만 남습니다 |
| 제안 기준 | 1.1 | 연관으로 보는 것보다 높게 둡니다 |
| 한 번에 최대 | 12개 | 제안이 쌓이면 사람은 전부 무시합니다 |
| 필요한 최소 메모 | 6개 | 이보다 적으면 판단하지 않습니다 |
| 쌍별 정확도 하한 | 0.65 | 임베딩이 의미를 판별한다고 볼 하한 |
| 최근접 동일 주제 하한 | 0.6 | 같은 주제끼리 묶이는지의 하한 |
| 측정 결과 보관 | 10분 | 측정 한 번은 문장 60개 임베딩 요청입니다 |

기준은 **코사인 값이 아니라 표준편차 단위**입니다. "그 후보 집합의 평균에서 몇 개 위인가"이므로, 임베딩 모델을 바꿔도 같은 뜻을 유지합니다(v0.9.0에서 도입한 방식).

범위를 벗어난 값은 **조용히 보정하지 않고 거부**합니다. 표준편차 칸에 40을 입력한 관리자에게는 그게 표준편차가 아니라고 말해 줘야지, umm이 몰래 1.1을 쓰면서 화면과 다르게 동작해서는 안 됩니다.

### 설정할 수 없는 것 하나

임베딩 판정 관문은 낮출 수 있지만, **어휘가 뜻을 앞서는 백엔드는 어떤 값으로도 통과하지 못합니다.** 판별력이 음수인 백엔드 — `PostgreSQL 백업 주기`와 `PostgreSQL 로고 색상`을 같은 것으로 보는 상태 — 는 설정의 문제가 아니라 바닥입니다. 관문 전체가 그걸 막으려고 존재합니다.

## 2. 게이트웨이 연결 테스트

지금까지 임베딩 게이트웨이가 동작하는지 확인하는 유일한 방법은 저장한 뒤 품질 리포트를 읽는 것이었습니다. 그런데 그 리포트는 **세 가지 다른 실패를 한 덩어리로** 보여 줍니다: 주소가 틀렸거나, 모델 이름이 틀렸거나, 모델은 도는데 의미를 못 재거나.

앞의 두 가지는 관리자가 이 화면에서 고칠 수 있는 것들이라 분리했습니다. **연결 테스트** 버튼이 실제로 두 문장을 임베딩해 보고 결과를 말합니다.

```
주소가 틀림   → dial tcp 127.0.0.1:1: connect: connection refused
모델이 없음   → status 404: model "never-pulled" not found, try pulling it first
정상          → ok · bge-m3 · 1024차원
```

저장된 API 키는 화면으로 되돌아오지 않으므로, 마스킹된 값이 오면 저장된 키를 씁니다. 복호화할 수 없는 키는 **암호문을 그대로 보내지 않고** 없는 것으로 취급합니다.

## 3. 작업 중 발견해 고친 것

### 기준을 바꿔도 즉시 반영되지 않았습니다

관문 판정은 캐시된 품질 리포트에서 나옵니다. 그런데 캐시 키는 백엔드 신원뿐이라, **관리자가 기준을 올려도 캐시가 만료될 때까지(최대 10분) 예전 판정이 그대로 쓰였습니다.** 실측으로 확인했습니다 — 정확도 하한을 0.99로 올렸는데 자동 연결이 계속 실행됐습니다.

측정값 자체는 기준과 무관하므로 **다시 재지 않고 다시 판정**하도록 고쳤습니다. 임베딩 요청이 추가로 나가지 않고, 설정 변경을 못 본 다른 인스턴스도 같은 숫자에서 같은 결론에 도달합니다.

### 설정 영역 목록이 두 군데 있었습니다

핸들러가 허용 영역 목록을 자체적으로 들고 있어서, 새 영역을 추가하려면 저장소와 핸들러 두 곳을 고쳐야 했습니다. 한쪽을 빠뜨리면 **"그런 설정 영역이 없습니다" 404**가 나는데, 이건 편집을 빠뜨렸다는 신호가 아니라 영역이 존재하지 않는다는 신호처럼 보입니다. 핸들러가 저장소의 목록을 쓰도록 합쳤습니다.

## 업그레이드

**마이그레이션이 있습니다** (012). 현재 상수와 똑같은 값을 넣으므로 **동작은 바뀌지 않습니다.**

```bash
docker run -d --name umm --restart unless-stopped \
  -p 8080:8080 \
  -e POSTGRES_DSN='postgres://umm:password@postgres.internal:5432/umm?sslmode=require' \
  -e BOOTSTRAP_ADMIN='admin' \
  -e BOOTSTRAP_ADMIN_PASSWORD='your-strong-password' \
  -e ENCRYPTION_KEY='your-32-char-random-encryption-key' \
  umm:v0.14.0
```

- 설정 행을 지워도 코드가 같은 값을 기본값으로 갖고 있어 동작은 같습니다. 관리자에게서 조절 수단만 사라집니다.
- 저장된 값이 범위를 벗어나 있으면(예: 수동으로 DB를 고친 경우) 해당 항목만 기본값으로 되돌아갑니다. 전체가 멈추지 않습니다.
