# v0.32.0 — 캔버스가 1MB씩 그대로 나가고 있었습니다

성능을 재던 중에 응답 크기를 봤습니다.

```
생각 2,010개 공간의 캔버스 응답 — 1,017,041 바이트
Accept-Encoding: gzip 을 보내도 — 1,017,041 바이트
```

**압축이 걸려 있지 않았습니다.**

## 왜 문제인가

기본 설치는 umm을 **직접 노출**합니다(`compose.yaml`의 `8080:8080`). 앞에 nginx나 Caddy를 두면
그쪽이 압축해 주지만, 문서가 안내하는 설치에는 그런 게 없습니다. 즉 공간을 열 때마다 1MB가 그대로
회선을 건너갑니다.

## 지금은

```
gzip 요청 시   1,017,041 → 65,424 바이트   (15.5배)
gzip 미요청    1,017,041 바이트 그대로     (기존 클라이언트 영향 없음)
```

로컬 루프백에서는 시간이 줄지 않습니다 — 회선이 없으니까요. **줄어드는 건 데이터**이고, 그게 실제
네트워크에서 의미가 있습니다.

## 첫 번째 시도는 스크립트를 놓쳤습니다

압축 목록에 `application/javascript`를 적었습니다. 그런데 Go가 `.js`에 붙이는 타입은
**`text/javascript`**입니다. 그래서 옆에 있는 스타일시트는 줄어드는데 435KB짜리 번들만 그대로
나갔습니다. **코드만 봐서는 멀쩡해 보이고, 응답을 봐야 보입니다.**

실제로 서버가 돌려주는 타입으로 목록을 맞췄습니다.

```
첫 화면 자산 전체   916,624 → 252,884 바이트  (3.6배)
  index.js         435,789 → 136,494
  index.css        344,457 →  67,815
  i18n.js          108,548 →  39,783
```

## 갓 만든 비밀이 담긴 응답은 압축하지 않습니다

공격자가 **길이를 관찰하면서 응답에 반영되는 내용을 바꿀 수 있으면** 압축은 BREACH의 형태가 됩니다.

umm의 CSRF 방어는 본문 토큰이 아니라 **Origin 기반**이라, 응답에 비밀이 등장하는 곳은 API 키와
웹훅 시크릿을 **처음 발급하는 네 경로뿐**입니다. 그 경로는 압축에서 뺐습니다 — 어차피 작은 객체
하나라서 잃는 것도 없습니다.

이미 그 경로들을 가리키는 정규식(`sensitiveCredentialPathPattern`)이 재시도 키 검사용으로 있었고,
같은 목록을 씁니다.

## 확인한 것

- 큰 JSON은 압축되고, 요청하지 않은 클라이언트는 그대로 받는지 테스트
- **서버가 실제로 돌려주는 타입 5종**이 압축되는지 테스트 (`text/javascript` 포함)
- **비밀을 담은 네 경로가 압축되지 않는지** 테스트 (`/api-keys`, `/api-keys/{id}/rotate`, `/webhooks`, `/webhooks/{id}/rotate-secret`)
- 실행 중인 인스턴스에서 실제 헤더와 바이트 수 확인
- 전체 Go 테스트 통과, e2e 19개 통과 (압축을 켠 채 브라우저로 전 과정 확인)
