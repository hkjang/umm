# v0.30.0 — 커진 공간에서 조용히 멈추지 않도록

기능을 여럿 붙이는 동안 **뜨거운 경로에 조회를 계속 더했습니다.** 재 보지 않았습니다. 그래서
쟀습니다.

## 2,000개짜리 공간에서

| 경로 | 시간 |
| --- | --- |
| 캔버스 전체 불러오기 | 1.48s |
| 검색 (갈래 표시 포함) | 0.021s |
| 갈래 + 소속 | 0.004s |
| 결정 기록 | 0.003s |
| 오늘의 리뷰 | 0.007s |
| 내보내기 | 0.67s |

v0.29.1에서 검색에 붙인 갈래 조회는 **21ms**입니다. 문제없습니다.

오늘의 리뷰가 7ms인 건 **중복 검사가 건너뛰어졌기 때문**입니다 — 이 데이터베이스는 어휘 임베딩을
쓰고 있었으니까요. 의미 백엔드에서는 그 경로가 돕니다.

## 중복 검사는 제곱으로 자랍니다

모든 쌍을 비교해야 하므로, 1024차원에서 직접 측정하면:

| 생각 수 | 쌍 | 시간 |
| --- | --- | --- |
| 500 | 124,750 | 58ms |
| 1,000 | 499,500 | **229ms** |
| 2,000 | 1,999,000 | **916ms** |
| 10,000 | 49,995,000 | **≈23초** |

**공간마다, 매일 아침**입니다. 몇 년 쌓인 공간이면 오늘의 리뷰가 조용히 타임아웃됩니다.

이제 한 공간에서 **1,000개까지만** 비교하고, 그 위로는 **그렇다고 말합니다.**

> 공간이 커서 최근 생각까지만 비교했습니다. 겹치는 것이 더 있을 수 있습니다.

`skipped`는 원래 이걸 위해 있는 자리입니다 — "위 목록이 비었다고 이상 없음으로 읽지 말 것".

## 처음엔 반대로 잘랐습니다

`ListNotes`가 최신순이라고 **가정하고** 앞에서 1,000개를 잘랐습니다. 확인해 보니
`ORDER BY n.created_at` — **오래된 것부터**입니다.

즉 **가장 오래된 1,000개**를 비교하고 최근 것을 버릴 뻔했습니다. 중복은 거의 언제나 최근 쪽에
있는데요. 그리고 **결과만 봐서는 아무것도 이상해 보이지 않습니다.**

그래서 자르는 부분을 `recentForDuplicateScan`으로 떼어 냈습니다 — 틀릴 수 있는 유일한 부분이라서요.
테스트를 고치기 전 코드로 돌려 실패를 확인했습니다:

```
the newest thought was dropped: kept ends at "999", space ends at "1049"
```

이 테스트는 백엔드가 필요 없습니다. 의미 백엔드에서만 도는 테스트는 CI에서 건너뛰어져 **아무것도
지키지 못합니다.**

## 부분적으로 봐도 표시는 붙습니다

잘라 낸 공간에서도 접어 둔 갈래 표시는 그대로 답니다. 오히려 **큰 공간이야말로 이미 거절한 결정을
다시 쓸 가능성이 높은 곳**입니다. 부족한 건 범위이고, 그 범위를 말해 줍니다.

## 확인한 것

- 전체 Go 테스트 통과, 웹 53개 통과, 타입·린트·i18n 통과
- 자르기 방향을 되돌려 테스트가 실제로 잡는지 확인
- 경계 아래 공간은 `skipped`를 내지 않는지 고정
