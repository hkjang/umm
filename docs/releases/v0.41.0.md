# v0.41.0 — 2000개 공간을 여는 데 7.5초, 이제 0.9초

성능 작업은 재기 전에는 시작할 수 없습니다. 실제 규모의 데이터를 넣고 재 봤습니다 —
공간 하나에 생각 2000개, 연결 1999개.

| | 이전 | 이후 |
| --- | ---: | ---: |
| **캔버스 열기 (브라우저)** | **7,570 ms** | **878 ms** |
| 캔버스 API | 243 ms | 88 ms |
| 묶음 보기 API | 321 ms | 111 ms |
| 오늘의 리뷰 | 307 ms | 82 ms |

## 브라우저가 2000장을 만들고 곧바로 버리고 있었습니다

가장 큰 것은 서버가 아니었습니다.

| | |
| --- | --- |
| 서버가 답한 시간 | 85 ms |
| 브라우저가 준비되기까지 | 7,570 ms |

측정해 보니 **+5.5초에 노드 2000개가 붙고, +8.6초에 1개로 바뀌었습니다.**

멀리서 보면 캔버스는 포스트잇 대신 묶음 상자를 그립니다. 그런데 *어느 쪽으로 열릴지*는
React Flow가 **모든 노트를 만들어 크기를 잰 뒤에야** 알 수 있었습니다. 그래서 2000장을 만들고,
재고, 전부 버린 다음 상자 한 개를 그렸습니다.

**잴 필요가 없는 일이었습니다.** 노트가 어디 있는지는 도착한 순간 이미 알고, 그것들을 담는
배율은 좌표 산수입니다.

산수는 **React Flow 자신의 함수**를 씁니다 — `fitView`가 쓰는 바로 그것. 여기에 베껴 두면
오늘은 맞고 저쪽이 여백 계산을 바꾸는 날 어긋나며, 그 어긋남은 **결국 도달할 화면으로 가는
길에 2000장이 깜빡이는 모습**으로 나타납니다.

### 처음 쓴 것은 틀렸습니다

예측이 계속 우선하게 만들었더니, 노트는 움직이지 않으니 **확대해도 영영 돌아오지 않았습니다.**
기존 테스트가 잡았습니다. 예측은 **어떻게 열릴지만** 정하고, 캔버스가 실제 위치를 보고하는
순간 물러납니다.

## 모든 쌍을 비교하던 것

캔버스를 열 때마다 공간의 **모든 노트 쌍**을 비교합니다 — 2000개면 200만 번. 포스트잇에
`관련 3` 배지를 붙이기 위해서입니다. 243ms 중 163ms였습니다.

벡터를 재 보니 **192차원 중 42개만 값이 있었습니다.** 나머지 150번의 곱셈은 **답이 0인 게
미리 정해진 산수**입니다.

건너뛰었더니 3.4배 빨라졌고, **결과는 한 비트도 다르지 않습니다.** 테스트가 "비슷하다"가 아니라
"같다"를 요구합니다 — 기준선이 그 점수들에서 나오고 다시 그 점수들과 비교되므로, 마지막
자리가 달라지면 경계에 있던 쌍이 선을 넘고 **사람이 읽는 정수가 바뀝니다.**

처음에 float32로 합산했다가 8번째 소수점에서 어긋났습니다. **"충분히 가깝다"로 들리지만
아닙니다.**

## 버린 결과를 위해 두 번 계산하던 것

묶음 보기는 노트를 불러오면서 `관련 N`을 계산하고 **읽지 않고 버린 뒤**, 자기 기준선을 위해
같은 쌍을 다시 비교했습니다. 이제 필요할 때만 셉니다.

## 검증

되돌려서 확인했습니다:

```
예측을 끄면        → 노드 최대 120개  (테스트 실패)
예측을 되돌리면    → 확대해도 노트가 안 돌아옴 (테스트 실패)
```

프레임마다 페이지 안에서 셉니다. 테스트 러너에서 폴링하면 **만들었다 지운 것이 두 폴링
사이로 빠져나갑니다** — 그런데 바로 그 "만들었다 버린 일"이 이 변경의 전부입니다.
