# v0.47.0 — 무엇을 승인하는지 보이게 했습니다

`검토 · 승인`은 이 프로젝트에서 **한 번도 제대로 본 적이 없는 화면**이었습니다. 승인 절차가
꺼져 있어 언제나 비어 있었고, 그래서 빈 화면만 확인하고 넘어갔습니다. 이번에 절차를 켜고
실제 요청을 넣어 봤습니다.

## 저장된 값이 그대로 화면에 나오고 있었습니다

```
admin   pending   export · space   2026. 8. 26.   [승인] [반려]
```

한국어 화면에 영어 내부 값이 그대로 있었습니다. 그런데 umm에는 **이미 이 말들이
있었습니다** — 이 절차를 켜는 관리자 화면이 바로 그 둘을 `팀 공간 공유`, `외부 내보내기`로
부르고 있습니다. 이 화면만 쓰지 않고 있었습니다.

| 나오던 것 | 지금 |
| --- | --- |
| `pending` | **검토 대기** |
| `approved` / `rejected` | **승인됨** / **반려됨** |
| `export · space` | **외부 내보내기** |
| `space_share · space` | **팀 공간 공유** |

## 무엇을 승인하는지가 없었습니다

더 큰 쪽입니다. `export · space` 는 대상의 **종류**만 말합니다. 어느 공간인지는 어디에도
없었습니다.

**내보내기를 허락할지 말지는 무엇을 내보내는지에 달려 있습니다.** 검토자가 판단해야 하는
바로 그 하나가 화면에 없었던 겁니다.

```
전:  외부 내보내기
후:  외부 내보내기
     제품 결정        ← 어느 공간인지
```

요청은 대상보다 오래 삽니다. 공간이 지워져도 요청은 **목록에 남고 검토할 수 있어야**
하므로 `LEFT JOIN` 입니다. 이름이 없으면 빈 줄 대신 `이름을 확인할 수 없는 대상`이라고
적습니다 — 빈 줄은 고장으로 읽힙니다.

## 검증

되돌려서 확인했습니다.

```
✘ 조회에서 공간 이름을 뺌        → "어느 공간인지 말하지 않음" 으로 실패
✘ LEFT JOIN 을 INNER JOIN 으로   → 지워진 공간의 요청이 사라져 실패
✘ 범위 조건 제거                 → 일반 사용자가 남의 요청까지 봄, 실패
✘ 저장된 값을 다시 그대로 출력    → E2E 실패
✘ 대상 이름을 화면에서 제거       → E2E 둘 다 실패
```

세 번째가 중요합니다. 조회를 한 줄로 합치면서 **관리자 · 팀장 · 본인** 세 범위가 한 곳으로
모였습니다. 넓히는 실수를 하기 쉬운 자리라 범위 자체를 테스트로 묶어 두었습니다.

## 덧: 확인 방법에 대한 기록

이번에 로컬 검증이 두 번 헛돌았습니다.

```
빈 DB 로 Go 테스트      → 실패. 그런데 손대지 않은 main 도 같은 실패
                          (스위트는 마이그레이션된 DB 를 전제로 합니다)
직접 만져 둔 DB 로 E2E   → admin-gateway 2개 실패
                          깨끗한 DB 에서는 통과 — 제가 남긴 설정 탓
```

둘 다 **코드가 아니라 확인 방법이 틀린 것**이었습니다. 실패를 봤을 때 손대지 않은 상태에서도
같은 실패가 나는지 먼저 확인하지 않으면, 없는 문제를 고치게 됩니다.
