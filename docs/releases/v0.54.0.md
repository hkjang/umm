# v0.54.0 — 카드에 적힌 숫자가 눌렀을 때 나오는 개수와 같아졌습니다

메모 카드의 `관련 N` 칩과, 그걸 눌러서 열리는 목록이 **다른 것을 세고 있었습니다.**

```
칩    공간의 모든 쌍에서 뽑은 기준선, cluster_band (1.1)
목록  그 생각 하나의 점수 분포에서 뽑은 기준선, related_band (0.6)
```

기본값이 다르니 둘은 **체계적으로 어긋납니다.** 생각 7개짜리 공간에서 재 봤더니 **5개가
불일치**했습니다.

```
생각 1   칩 1  ↔  목록 3
생각 2   칩 0  ↔  목록 2      ← 칩이 아예 안 뜹니다
생각 3   칩 0  ↔  목록 1      ← 칩이 아예 안 뜹니다
생각 6   칩 0  ↔  목록 1      ← 칩이 아예 안 뜹니다
```

**0이 가장 나쁩니다.** 개수가 0이면 칩 자체가 렌더되지 않으므로, 관련된 생각이 있는데도
아무도 그 사실을 알 수 없습니다.

## 이제 같은 선을 씁니다

칩도 목록과 똑같이 **그 생각 자신의 점수 분포**에서 기준선을 뽑습니다. 칩의 숫자는
"눌렀을 때 나오는 개수"입니다.

목록에 표시 개수 상한이 있어도 숫자는 **전체**를 말합니다 — 이 코드베이스가 이미 지키는
원칙(`counts the queue, not the page it happens to have loaded`)과 같습니다.

## 비용을 재 봤습니다

처음에는 "생각마다 기준선을 다시 뽑으면 비싸다" 고 판단해 **미뤘습니다. 그 판단이
틀렸습니다.**

기준선은 정렬이 아니라 **평균과 표준편차**로 구합니다 — 한 줄당 선형입니다. 그리고 쌍 점수는
이미 한 번 계산해 두므로, 각 줄은 곱셈을 다시 하지 않고 **색인으로 읽어옵니다.**

```
생각 2000개   기존 48.5ms  →  63.0ms   (+29%, 14ms)
```

10배를 걱정했는데 1.3배였습니다. 재 보지 않고 미룬 것이 잘못이었습니다.

## 검증

```
✘ 칩을 다시 cluster_band·전체 쌍으로  →  7개 중 5개가 어긋나 시험 실패
                                        (생각 2·3·6은 0 ↔ 1~2)
```

새 계산은 **뻔한 이중 루프와 같은 값**인지로 검증합니다 — 근사가 아니라 정확히 같은 정수로.
대칭인 쌍을 한 번만 저장해 두고 양쪽에서 읽는 색인 계산이 조용히 엉뚱한 줄을 세는 일이
없도록, 그 부분을 특히 겨눕니다.

기존 `TestRelatedCountMatchesTheFullSquare` 도 새 규칙의 뻔한 버전으로 바꿨습니다. 이
시험의 목적은 "빠른 구현이 뻔한 구현과 같다" 이고, 뻔한 구현이 바뀌었기 때문입니다.

## 눈에 보이는 변화입니다

`related_band` 가 더 느슨하므로 **칩이 더 많이, 더 큰 숫자로 나타납니다.** 없던 관련성을
만들어 낸 것이 아니라, 목록에 이미 있던 것을 카드가 이제 말해 주는 것입니다. 되돌리려면
`store.go` 의 한 줄입니다.
