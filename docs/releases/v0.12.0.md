# umm v0.12.0 — umm이 연결을 먼저 제안합니다

v0.11.0에서 연결에 뜻(`relation`)과 출처(`origin`), 그리고 `confidence` 칸을 만들었습니다. `origin='auto'`는 그때 아무도 쓰지 않는 값이었습니다. 이번 릴리스가 그것을 씁니다.

**umm이 스스로 사람의 기억에 쓰는 첫 기능입니다.** 그래서 설계의 대부분은 "무엇을 제안할까"가 아니라 "언제 제안하지 않을까"에 들어갔습니다.

---

## 1. 판단할 수 없으면 추측하지 않습니다

가장 중요한 결정입니다.

v0.10.0에서 측정했듯 기본 로컬 임베딩은 **뜻이 같은 문장보다 단어가 겹치는 문장을 높게** 봅니다(쌍별 정확도 4.2%, 최근접 동일 주제 18.8%). 이 백엔드로 연결을 제안하면 `PostgreSQL 백업 주기`와 `PostgreSQL 로고 색상`을 이어 놓고 발견이라고 부르게 됩니다.

그래서 자동 연결은 **umm 자신의 측정을 관문으로 씁니다.** 백엔드가 의미를 판별한다고 측정되지 않으면 실행 자체를 거부하고, 왜 거부했는지 말합니다.

```
POST /spaces/{id}/links/suggest
→ {"outcome":"backend-not-semantic","edges":[],"considered":0}
```

화면에는 이렇게 나옵니다.

> 지금 임베딩이 뜻이 아니라 겹치는 단어를 재고 있어 추천을 만들지 않았습니다.
> 관리자 → AI Gateway에서 임베딩 모델을 설정하면 켜집니다.

세 릴리스가 여기서 맞물립니다. **v0.9.0**의 분포 상대 기준이 "유난히 가깝다"의 선을 긋고, **v0.10.0**의 측정이 umm이 판단할 자격이 있는지 정하고, **v0.11.0**의 스키마가 그 판단이 추측임을 기록합니다.

`outcome`은 네 가지로 구분됩니다. 조용한 결과에도 종류가 있고, "찾지 못했다"와 "판단을 거부했다"는 전혀 다른 대응을 부릅니다.

| outcome | 뜻 |
| :--- | :--- |
| `suggested` | 하나 이상 제안했습니다 |
| `no-candidates` | 판단은 했고, 눈에 띄는 것이 없었습니다 |
| `backend-not-semantic` | 판단할 수 없는 백엔드라 추측하지 않았습니다 |
| `too-few-notes` | 무엇이 "유난히"인지 말하기에 생각이 적습니다 |

---

## 2. 제안은 제안으로 보입니다

제안은 `origin='auto'`와 `confidence`를 달고 그래프에 기록됩니다. 사라지는 목록이 아니라 실제 엣지인 이유는, 지금 답하지 않으면 없어지는 제안은 없느니만 못하기 때문입니다.

캔버스에서 추천은 애니메이션으로 구분되고, 검토 패널에서 **남기기**(→ `origin='manual'`, confidence 삭제) 또는 **추천 지우기**(→ 삭제)를 고를 수 있습니다.

`confidence`는 확률이 아닙니다. **이 공간의 다른 짝들에 비해 얼마나 두드러지는지**이고, 화면에도 그렇게 적혀 있습니다. 그 이상은 측정이 뒷받침하지 않습니다.

실제 배포에서 bge-m3로 확인한 결과입니다. 보안 3 + 자전거 3, 15개 짝 중 3개를 제안했고 **주제를 넘는 제안은 없었습니다.**

```
0.53  주말에 자전거를 타고 한강을 따라 달렸다  ↔  자전거 체인에 기름을 새로 발랐다
0.53  자전거 체인에 기름을 새로 발랐다        ↔  라이딩이 끝나면 스트레칭을 꼭 한다
0.52  인증 토큰 만료 시간을 24시간으로 정했다  ↔  로그인 실패가 반복되면 계정을 잠근다
```

## 3. 실제로 돌려 보고 찾은 결함

기능을 다 만들고 실제 인스턴스에서 흐름을 밟다가 발견했습니다.

자동 연결은 **이미 연결된 짝을 건너뜁니다.** 그런데 추천을 지우면 그 엣지가 사라지고, 그러면 건너뛸 근거도 함께 사라집니다. **다음 실행에서 방금 지운 추천이 그대로 다시 올라왔습니다.**

```
run 1: suggested 3 edges
discard: 204
run 2: suggested 1 edge   ← 방금 지운 그것
```

지울 수 없는 추천은 없느니만 못합니다. 마이그레이션 011로 거절을 별도로 기억하게 했습니다. 짝은 방향과 무관하게 정규화해 저장합니다 — 두 생각 사이의 연결은 umm이 어느 쪽으로 놓았든 같은 연결이기 때문입니다.

```
run 2 after discard: no-candidates 0 edges
1 dismissal remembered
```

**사람이 그은 연결을 지우는 것은 다릅니다.** 나중에 다시 제안받고 싶을 수 있으므로, 거절 기록은 추측한 엣지에만 남습니다.

기존 테스트는 이걸 잡지 못했습니다. 두 번 연달아 실행하기만 하고 **중간에 지우지 않았기** 때문입니다. 그 경로를 테스트로 고정했습니다.

---

## 4. 연결 삭제

여기까지 오면서 알게 된 것인데, umm에는 **연결을 지우는 방법이 아예 없었습니다.** 실수로 그은 선은 영원히 남았습니다. `DELETE /edges/{id}`가 생겼고, 추천을 거절하는 경로이기도 합니다.

---

## 5. 그 밖에

- 거부 경로에서 `edges`가 `null`로 나가던 것을 빈 배열로 고쳤습니다. 명세는 배열이라고 적혀 있었고, 결과를 순회하는 클라이언트가 거부 응답에서 깨질 수 있었습니다. 실제로 돌려 보다가 발견했습니다.
- v0.11.0에서 넣은 i18n 중복 키 검사가 이번 작업 중 만든 중복을 바로 잡았습니다. `지우기`가 이미 `Delete`로 번역되어 있어, 추천 거절은 `추천 지우기`로 분리했습니다.
- 테스트 하네스에서 실제 백엔드가 쓰였는지 확인하지 않아 순서에 따라 통과/실패하던 문제를 고쳤습니다. `PutSetting`이 `api_key`를 의도적으로 보존하기 때문에 다른 테스트가 남긴 `enc:` 키가 살아남아 provider가 조용히 로컬로 닫히고 있었습니다. **제품은 옳게 동작했고 테스트가 스스로를 속이고 있었습니다.**

## 업그레이드

**마이그레이션이 있습니다** (011). 이미지를 올리면 자동 적용됩니다.

```bash
docker run -d --name umm --restart unless-stopped \
  -p 8080:8080 \
  -e POSTGRES_DSN='postgres://umm:password@postgres.internal:5432/umm?sslmode=require' \
  -e BOOTSTRAP_ADMIN='admin' \
  -e BOOTSTRAP_ADMIN_PASSWORD='your-strong-password' \
  -e ENCRYPTION_KEY='your-32-char-random-encryption-key' \
  umm:v0.12.0
```

알아 두면 좋은 것:

- **임베딩 모델을 설정하지 않은 배포에서는 추천 버튼이 이유를 설명하고 아무것도 만들지 않습니다.** 이것이 의도된 동작입니다. 켜려면 `docs/admin-guide.md`의 오프라인 임베딩 서버 항목을 보세요.
- 추천은 실제 엣지로 저장되므로 협업 중인 공간에서는 다른 구성원에게도 보입니다. 추천으로 표시되며, 누구든 남기거나 지울 수 있습니다.
- 한 번 실행에 최대 12개까지만 제안합니다. 제안이 쌓이면 전부 무시하게 되기 때문입니다.
