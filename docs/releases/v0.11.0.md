# umm v0.11.0 — 연결에 뜻과 출처를 붙이다

Memory Graph의 첫 단계입니다. 로드맵의 다음 축들 — 모순 감지, 의미 자동 연결, Ask My Memory, Agent Memory — 은 전부 "이 두 생각은 어떤 관계인가"와 "그 관계를 누가 주장했는가"를 알아야 성립합니다. v0.11.0은 그 두 가지를 기록하기 시작합니다.

---

## 1. 먼저 확인한 것: 연결은 검증되지 않고 있었습니다

`note_edges.relation`은 요청 본문에서 온 자유 텍스트였고, 출처를 기록하는 칸은 아예 없었습니다. 실제 인스턴스에 요청을 보내 확인했습니다.

```
POST /api/v1/spaces/{id}/edges  {"relation":"dreamed"}
→ 201 Created

DB: relation=dreamed
```

**일반 사용자가 "umm의 Dream이 이 연결을 발견했다"고 주장하는 엣지를 만들 수 있었습니다.** 진짜 Dream이 만든 것과 구별할 방법이 없었습니다. 5000자짜리 relation도 그대로 저장됐고, 캔버스는 그것을 라벨로 렌더링했습니다.

밑에 깔린 모델링 오류는 하나입니다. `relation`이 **뜻**과 **만든 주체**를 한 칸에 담고 있었습니다. `dreamed`는 관계를 설명하지 않고 도구를 가리켰습니다.

### 위조로 할 수 있었던 일의 범위

정직하게 적자면, `expanded` 위조가 영향을 주는 코드 경로는 Dream 확장 노트의 **세로 배치 위치** 하나뿐이었습니다. 권한이나 데이터 유출로 이어지지는 않습니다.

문제는 무결성입니다. 내보내기는 `--dreamed-->`를 그대로 적고, 앞으로 올 모순 엔진과 자동 연결은 "이 주장을 누가 했는가"를 신뢰할 수 있어야 합니다. 신뢰할 수 없는 출처 위에 추론을 쌓으면 쌓은 만큼 틀립니다.

---

## 2. 뜻과 출처를 분리했습니다

`relation`은 이제 **뜻만** 담고, 검사된 어휘입니다.

| 관계 | 뜻 |
| :--- | :--- |
| `related` | 함께 묶인다 (기본) |
| `supports` | 출발점이 도착점을 뒷받침한다 |
| `contradicts` | 둘이 동시에 옳을 수 없다 |
| `refines` | 도착점이 출발점을 더 정확히 말한다 |
| `expands` | 도착점이 출발점에서 발전했다 |
| `follows` | 도착점이 출발점 다음에 온다 |

`origin`은 **만든 주체만** 담고, 요청 본문에서 절대 읽지 않습니다.

| 출처 | 언제 |
| :--- | :--- |
| `manual` | 사람이 웹에서 선을 그림 |
| `agent` | MCP로 에이전트가 주장 |
| `dream` | Dream을 공간에 받아들일 때 |
| `development` | Dream 확장이 생각이 될 때 |
| `import` | 문서를 가져올 때 |
| `auto` | umm이 스스로 추론 (다음 단계) |

`confidence`도 지금 넣었습니다. `auto`일 때만 값이 있고, 그 외에는 반드시 비어 있습니다 — 제약으로 강제됩니다. **사람이 선을 그은 것은 확률의 표현이 아닙니다.**

어휘 밖의 값은 조용히 `related`로 바꾸지 않고 **거부**합니다. 사용자가 설명하지 않은 연결을 기록하고 실수를 감추는 대신, 무엇이 가능한지 알려 줍니다.

```
POST {"relation":"dreamed"}
→ 400  {"allowedRelations":["related","supports","contradicts","refines","expands","follows"]}
```

### 한 쌍에 여러 관계

`UNIQUE(source, target)`은 관계에 뜻이 없을 때는 맞는 제약이었습니다. 이제 두 생각이 서로를 뒷받침하면서 동시에 구체화할 수 있고, 기계 추천이 사람이 그은 선을 덮어써서도 안 됩니다. `UNIQUE(source, target, relation)`으로 바꿨습니다.

역방향 탐색(`이 생각을 무엇이 가리키는가`)에는 인덱스가 아예 없어 전체 스캔이었습니다. 추가했습니다.

## 3. 화면과 내보내기가 출처를 말합니다

캔버스에서 애니메이션은 이제 **관계가 아니라 출처**를 표시합니다. umm이 만든 선과 사람이 그은 선이 달라 보여야 하기 때문입니다. 라벨은 원문 식별자 대신 번역된 이름을 씁니다.

툴바에 **연결 종류 선택**이 생겼습니다. 선을 그을 때마다 물어보지 않고 모드로 둔 이유는, 모순을 표시하는 사람은 여러 개를 연달아 긋기 때문입니다. 선택은 브라우저에 남습니다.

내보내기도 출처를 적습니다. 내보낸 문서는 umm이 없어진 뒤에 남는 것이라, 어떤 연결을 사람이 그었고 어떤 것을 소프트웨어가 만들었는지 페이지 위에서 구별돼야 합니다.

```
- `id` --related--> `id` (dream)
- `id` --contradicts--> `id`
```

MCP의 `connect_notes`도 그대로 두지 않았습니다. 에이전트가 만든 연결은 `origin=agent`로 기록되며, 사람이 그은 것으로 표시될 수 없습니다. 에이전트가 기억에 쓰기 시작하면, 소유자는 어느 부분을 에이전트가 썼는지 볼 수 있어야 합니다.

## 4. 마이그레이션이 실제 데이터에서 되돌아가는지 확인했습니다

`migrate-dry-run.sh`는 빈 스키마에서 돕니다. 010이 위험한 부분은 **데이터를 옮기는 경로**입니다: 옛 relation에서 출처를 복구하고, 검증되지 않은 문자열을 `legacy_relation`에 보관하고, 롤백 시 한 쌍당 하나로 되돌리며 행을 지우는 곳.

`scripts/graph-migration-drill.sh`가 그 형태들을 심어 놓고 앞뒤로 굴립니다. CI에 넣었습니다.

```
ok  dream provenance recovered = related|dream
ok  unvalidated relation parked, not destroyed = related|manual|5000
ok  four relations on one pair = 4
ok  one edge per pair restored = 1
ok  the surviving edge is the original = dreamed
ok  original relation text returned intact = 5000
```

### 백필이 되돌릴 수 없는 것

기존 `dreamed` 엣지는 `origin='dream'`으로 옮겨집니다. **이번 릴리스 전에 위조된 것이 있다면 그대로 보존됩니다.** 구별에 필요한 정보가 애초에 기록된 적이 없기 때문입니다. 앞으로는 요청 본문에서 그 주장을 할 수 없고, 기존 행은 달리 볼 근거가 없어 액면 그대로 받습니다.

## 5. 그 밖에

i18n 검사가 **중복 키**를 잡습니다. 작업 중 실제로 하나 만들었고, `tsc --noEmit`은 놓쳤으며 빌드 단계에서야 걸렸습니다. 뒤에 온 항목이 조용히 이기므로, 한 문구의 번역 두 개가 서로 달라도 한쪽만 화면에 나옵니다.

## 업그레이드

**마이그레이션이 있습니다** (010). 이미지를 올리면 자동 적용됩니다.

```bash
docker run -d --name umm --restart unless-stopped \
  -p 8080:8080 \
  -e POSTGRES_DSN='postgres://umm:password@postgres.internal:5432/umm?sslmode=require' \
  -e BOOTSTRAP_ADMIN='admin' \
  -e BOOTSTRAP_ADMIN_PASSWORD='your-strong-password' \
  -e ENCRYPTION_KEY='your-32-char-random-encryption-key' \
  umm:v0.11.0
```

알아 두면 좋은 것:

- API나 MCP로 **어휘 밖의 relation을 보내던 클라이언트는 이제 400을 받습니다.** 기존에 저장된 그런 값들은 `related`로 옮겨지고 원문은 `legacy_relation`에 남습니다.
- 캔버스에서 Dream 연결의 애니메이션 기준이 relation에서 origin으로 바뀝니다. 보이는 결과는 거의 같습니다.
- 롤백이 필요하면 `migrations/down/010_memory_graph.down.sql`이 원래 문자열까지 복원합니다. 다만 010 이후에 한 쌍에 여러 관계를 만들었다면 가장 오래된 것만 남습니다.
