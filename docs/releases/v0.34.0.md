# v0.34.0 — 임베딩 Gateway를 따로 지정할 수 있습니다

임베딩과 채팅 모델이 같은 서버에 있을 이유는 없습니다. 큰 모델은 강한 장비에 두고 임베딩은 umm 옆에
작게 띄우는 편이 흔하고, **`compose.yaml`의 `embeddings` 프로파일이 정확히 그 모양**입니다.

그런데 지금까지는 둘이 **같은 `base_url`을 공유**해야 했습니다.

## 무엇이 생겼나

관리자 → AI Gateway에 두 칸이 추가됐습니다.

| 항목 | 비우면 | 적으면 |
| :--- | :--- | :--- |
| **임베딩 Gateway 주소** | 위의 Base URL을 씁니다 — **기존 동작 그대로** | 임베딩만 이 주소로 |
| **임베딩 API Key** | 인증 헤더를 **보내지 않습니다** | 이 키로 인증 |

기존 설치는 새 칸이 비어 있으므로 **아무것도 달라지지 않습니다.**

## 채팅 API Key는 임베딩 주소로 따라가지 않습니다

이건 편의가 아니라 **주소를 나눌 수 있게 만든 대가로 반드시 지켜야 하는 규칙**입니다.

한 호스트에 발급된 키는 그 호스트의 자격증명입니다. 임베딩 키를 비워 뒀다는 이유로 채팅 키를 대신
보내면, **그 서버를 운영하는 사람에게 키를 건네주는 셈**입니다. 인증이 필요 없는 임베딩 서버가 흔한
상황이므로 **비움 = 보내지 않음**으로 정했습니다.

실제로 확인했습니다. 채팅 주소를 요청을 기록하는 서버로 두고, 임베딩만 ollama로 보냈습니다.

```
임베딩 백엔드 : bge-m3   (쌍별 정확도 0.833)
채팅 서버가 받은 것 : 없음
```

## 잘못된 주소는 거부합니다

조용히 무시하면 임베딩이 내장 알고리즘으로 돌아간 채 **설정 화면에는 저장된 값이 그대로** 보입니다.
설정한 사람은 아무것도 잘못한 줄 모릅니다.

```
embedding_base_url: "not a url"  →  400 임베딩 Gateway URL이 올바르지 않습니다
```

## 비밀 값이 두 개가 되면서

마스킹과 암호화가 `api_key` 하나만 알고 있었고, **읽는 쪽과 쓰는 쪽이 각자 필드 이름을 적어 두고**
있었습니다. 한 곳만 고치면 키가 평문으로 조회되는 구조라, 목록을 하나로 합쳤습니다.

두 키 모두 조회 시 `••••••••`로 가려지고, 가려진 채로 저장해도 기존 값이 보존됩니다.
